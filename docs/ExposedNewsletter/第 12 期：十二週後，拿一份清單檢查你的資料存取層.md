# 十二週後，拿一份清單檢查你的資料存取層

十二週後，你手上多了一堆寫法，卻不知道自己的資料存取層到底穩不穩。

這是十二期系列的最後一封信。系列從一行連線，走到關聯與查詢次數。這封信不教新東西，只把走過的路收斂成一份可以直接對著專案檢查的清單。五個層次，十二個問題。答不出來的那一題，就是你接下來要補的功課。

## 連線與交易

- 連線字串與驅動，換資料庫時只需要改這兩處嗎？
- 每個資料庫操作，都包在範圍明確的 `transaction` 區塊裡嗎？

## 資料表定義

- 資料表定義集中在一處，查詢都引用它，沒有散落的欄位字串嗎？
- 你清楚區分了開發時用的自動建表，與正式環境需要的遷移工具嗎？

## 寫法選擇

- 專案裡 DSL 與 DAO 的使用界線，團隊有約定嗎？
- 更新與刪除之前，你會先用相同的條件寫一次查詢檢查影響範圍嗎？

## 關聯

- 一對多與多對多的關係，都在資料表定義時宣告清楚了嗎？
- 標籤這類多對多資料，有拆成中介資料表，沒有塞在字串裡嗎？

## 查詢次數

- 你開過 SQL 日誌，數過列表頁實際發了幾條查詢嗎？
- 迴圈裡讀取關聯資料的地方，都確認過有沒有 N+1 嗎？
- 需要一次載入關聯的地方，用了 eager loading 嗎？
- 慢的時候，你的第一個動作是看日誌嗎？

## 這個系列沒有講的

清單通過，代表資料存取層有了站得住的基礎。這個系列刻意沒碰的幾塊，全部列入後續待辦：

- 連線池調校。
- 資料庫遷移工具。
- 協程中的交易，也就是在非同步的程式碼裡怎麼安全地操作資料庫，這部分在 Ktor Tips 的另一期有談，請以該期對照你使用的 Exposed 版本。
- 自動測試，與測試替身的使用。
- 對外提供資料的 API Server。

回頭看第一封信的問題：不想拼 SQL 字串，也不想被 ORM 綁架。現在你的查詢都在編譯器的檢查之內，也看得到每一條實際送出的 SQL，這兩件事，你做到了嗎？

謝謝你讀完這十二封信。身邊如果有朋友正在評估 Exposed，把這份清單轉給他。

回信告訴我，這十二題裡你的專案答不出來的是哪一題。如果這封信是朋友轉給你的，歡迎訂閱，每週一封。
