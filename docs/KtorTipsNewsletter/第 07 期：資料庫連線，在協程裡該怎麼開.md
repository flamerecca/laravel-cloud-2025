# 資料庫連線，在協程裡該怎麼開

換成 Exposed 之後，團隊裡有人把 Eloquent 的習慣帶了過來：撈出十筆訂單，在迴圈裡一筆一筆查明細。程式跑得好好的，直到壓測才發現資料庫被打爆。

Ktor 核心不含 ORM，Exposed 是 JetBrains 維護的 Kotlin 函式庫，也是常見的選擇之一。這封信只談最小可用的接法，並不比較各種 ORM。先提醒一件事：Exposed 的 API 在不同版本之間有調整，下面的寫法請對照你實際使用的版本。

## 最小的接法

連線池用 HikariCP，表定義用 Exposed 的 `Table`：

```kotlin
val dataSource = HikariDataSource(HikariConfig().apply {
    jdbcUrl = "jdbc:postgresql://localhost:5432/shop"
    username = "app"
    password = "secret" // 示意，密鑰的處理留到部署那一期
    maximumPoolSize = 10
})
Database.connect(dataSource)

object Orders : LongIdTable("orders") {
    val customerId = long("customer_id")
    val status = varchar("status", 20)
}
```

連線池大小先不用調校，十個連線通常夠你開始。

## 協程裡的交易

JDBC 本身是阻塞式的。如果直接在 handler 裡開一般的交易，就把前一封信談過的問題帶回來了：阻塞呼叫占住處理請求的執行緒。Exposed 提供協程友善的交易寫法，會把阻塞工作放到你指定的 Dispatcher 上：

```kotlin
suspend fun findByCustomer(customerId: Long) =
    newSuspendedTransaction(Dispatchers.IO) {
        Orders.selectAll().where { Orders.customerId eq customerId }
            .map { it[Orders.id].value to it[Orders.status] }
    }
```

## 沒有人替你警告的 N+1

先看會出事的寫法：

```kotlin
val orders = findByCustomer(customerId)
orders.forEach { (id, _) -> itemRepository.findByOrder(id) } // 每筆訂單一次查詢
```

十筆訂單就是十一次查詢，一百筆就是一百零一次。用 Exposed 的 join 一次查完：

```kotlin
(Orders innerJoin OrderItems)
    .selectAll().where { Orders.customerId eq customerId }
```

要讓 `innerJoin` 成立，`OrderItems` 需要用 `reference` 宣告對 `Orders` 的外鍵。

重點在於，沒有任何東西會在開發階段警告你。Ktor 不會，Exposed 也不會。我的建議是兩件事並行：開發時在交易裡加上 `addLogger(StdOutSqlLogger)`，把實際送出的 SQL 印出來，一眼看得到重複的查詢。再來是 code review 時，只要看到迴圈裡有資料庫呼叫，就停下來問一句。

資料庫接好、Repository 與 Service 一多，物件之間怎麼接在一起就成了新問題。下一封信談這件事。
