# Spring Boot 搭配 Kotlin 基礎開發：從 Initializr 到一支能驗證、能測試的服務

一份三個月、12 期的電子報企劃。寫給已經會寫 Kotlin 語法，第一次碰 Spring Boot，專案產生之後面對一堆檔案與標註，不知道哪些該先搞懂的後端工程師。

這個系列的素材來自 [[2026 Kotlin + SpringBoot 基礎教學]]。課綱在課堂上用 12 小時帶學員做出一個完整的小服務，電子報把同一條路線拆成 12 個讀者在動手時會撞到的具體問題，每週一個，讓沒有上課的人也能走完。

每一期是一封獨立的信，不假設你追過前面幾期，每封信只講一件事，篇幅控制在一次通勤或一杯咖啡的時間看得完。

**這封信要做的事**：導覽剛產生的專案，只講三樣：`build.gradle.kts` 宣告了什麼依賴與外掛，設定檔放什麼，帶有 `@SpringBootApplication` 的進入點做了什麼。其他東西先貼上「之後會用到」的標籤。同時用一句話帶出本系列貫穿的片段庫情境。

**讀完應該記住**：第一天只需要看懂三個地方，其餘的用到再看。

**如果你沒看過前面幾期**：這是系列第一期，不需要任何背景知識。

### 第 2 期：為什麼 Kotlin 類別在 Spring 裡突然要加 open

**寫給誰看**：從 Java 的教學複製了範例，在 Kotlin 裡遇到 Spring 抱怨類別是 final 的人。

**這封信要做的事**：說明 Kotlin 類別預設是 final，而 Spring 為了替類別產生代理，需要它們可被繼承。介紹 `kotlin-spring` 外掛會替帶有 Spring 標註的類別自動處理這件事，讀者不需要手動加 `open`。先讓讀者看到不用外掛時的錯誤，再看外掛如何消除它。

**讀完應該記住**：Kotlin 與 Spring 的摩擦點被一個編譯外掛吸收了，知道它存在，就不會被錯誤訊息嚇到。

**如果你沒看過前面幾期**：不依賴前情，用一句話帶出 Spring 會替類別產生代理。

**收尾**：邀請讀者貼出自己第一次遇到的 Kotlin 與 Spring 相關錯誤訊息。

---

### 第 3 期：誰來負責 new

**寫給誰看**：看到 `@Service` 與建構子參數，不知道物件是誰建立的、為什麼不用自己 `new` 的人。

**這封信要做的事**：用片段庫的 `SnippetService` 與一個依賴它的類別，說明依賴注入：類別宣告自己需要什麼，由容器負責建立與組裝。說明在 Kotlin 裡主建構子搭配 `val` 的建構子注入，為什麼比欄位注入更自然。最後用一小段說明 `@Component`、`@Service`、`@Repository` 技術上相近，語意上標示不同角色。

**讀完應該記住**：類別只管宣告需求，建立與組裝交給容器。

**如果你沒看過前面幾期**：用一句話交代 `@Service` 是告訴 Spring 這個類別由它管理。

**收尾**：邀請讀者說出自己習慣的注入方式與原因。

---

### 第 4 期：五個端點怎麼寫，參數各用哪個註解拿

**寫給誰看**：要做 CRUD 端點，分不清路徑參數、查詢參數與請求主體各該用哪個註解的人。

**這封信要做的事**：用 `SnippetController` 實作列出、查詢單筆、新增、更新、刪除五個端點，並用三個註解區分資料來源：路徑參數取單筆、查詢參數做語言篩選、請求主體傳新增內容。順帶說明請求與回應用 Kotlin 資料類別定義的好處。

**讀完應該記住**：資料從哪裡來，就用對應的註解去拿，並用資料類別描述形狀。

**如果你沒看過前面幾期**：用一句話交代控制器是接收 HTTP 請求的類別。

**收尾**：邀請讀者回信說出自己最想先做出來的那個端點。

### 第 5 期：全部回 200 的 API，前端怎麼知道出事了

**寫給誰看**：API 不管成功失敗都回 200，由前端去解析本文才知道結果的人。

**這封信要做的事**：說明狀態碼是 API 對呼叫方的第一層溝通。用 `ResponseEntity` 示範新增回 201 並帶回新建資料，查無資料回 404。說明選擇狀態碼的簡單原則，並指出這封信只處理主要路徑，錯誤的統一格式留到後面。

**讀完應該記住**：狀態碼讓呼叫方不用解析本文，就知道發生了什麼事。

**如果你沒看過前面幾期**：用一句話交代 `ResponseEntity` 可以同時指定狀態碼與本文。

**收尾**：邀請讀者檢查自己手上的 API，有哪一支一律回 200。

---

### 第 6 期：Entity 需要無參數建構子，Kotlin 類別怎麼辦

**寫給誰看**：用 Kotlin 資料類別宣告了 JPA Entity，執行時卻被要求無參數建構子的人。

**這封信要做的事**：這是全系列最容易卡關的一期。先重現錯誤訊息，說明 JPA 需要無參數建構子，而 Kotlin 主建構子沒有提供。介紹 `kotlin-jpa` 外掛如何自動補上，並示範 `Snippet` Entity 的宣告。誠實提醒：資料類別直接當 Entity 在相等判斷與關聯載入上有取捨，需要查證後再下結論。

**讀完應該記住**：錯誤訊息的原因是 JPA 的建構限制，外掛已經替你處理，不用修改類別設計。

**如果你沒看過前面幾期**：用一句話交代 Entity 是對應資料表的類別。

**收尾**：邀請讀者回信貼出自己第一次遇到的 Entity 相關錯誤。

### 第 7 期：不寫 SQL，findByLanguage 為什麼就能查

**寫給誰看**：看到只宣告了一個介面方法就能查詢，覺得像魔法，不敢相信也不敢改的人。

**這封信要做的事**：說明繼承 `JpaRepository` 就取得基本 CRUD，並用 `findByLanguage` 示範衍生查詢：Spring 依方法名稱解析成查詢。說明命名慣例的規則與界線，什麼時候名稱已經長到不該再用這種寫法。

**讀完應該記住**：方法名稱本身就是查詢的描述，慣例明確，也有明確的使用界線。

**如果你沒看過前面幾期**：用一句話交代 Repository 是資料存取介面。

**收尾**：邀請讀者想一個自己想用方法名稱表達的查詢條件。

### 第 8 期：把記憶體換成資料庫，API 一行都不用改

**讀完應該記住**：分層做對了，換資料來源只需要改一層。

**如果你沒看過前面幾期**：用一句話交代 Service 負責業務邏輯，控制器負責接收請求。

### 第 9 期：標題留空，API 應該回什麼

**寫給誰看**：請求資料沒有任何確認，空標題也能存進資料庫的人。

**讀完應該記住**：確認規則寫在資料類別上，寫完要實際送一次錯的資料驗證它有效。

### 第 10 期：三支 API 三種錯誤格式

**寫給誰看**：每個控制器方法各自處理例外，結果同一個服務有好幾種錯誤回應的人。

**這封信要做的事**：用 `@RestControllerAdvice` 搭配 `@ExceptionHandler`，把驗證失敗與查無資料統一轉成固定形狀的錯誤回應。說明統一格式對前端的價值，並提醒內部細節不該流到回應裡。

**讀完應該記住**：錯誤處理集中在一個地方，每支 API 才會用同一種方式說「出事了」。

**如果你沒看過前面幾期**：用一句話交代例外沒人接住時，預設會回什麼。

**收尾**：邀請讀者回信說出自己團隊現在的錯誤格式有幾種。

## 待確認事項

動筆前需要先查證，否則容易與實際行為矛盾。

2. **兩個編譯外掛**：`kotlin-spring` 與 `kotlin-jpa` 在 Gradle Kotlin DSL 的啟用寫法與實際錯誤訊息，第 2、6 期需要先重現再寫。

5. **測試寫法**：`@SpringBootTest` 與 `MockMvc` 在目前版本的注入與設定寫法，第 11 期範例必須實際執行通過。
6. **與課綱的先備範圍**：本系列假設讀者已有 Kotlin 基礎，不重教語法，遇到需要的語法只用一句話帶過。

## 給撰寫每一期正文時的提醒

1. **篇幅落在 800 到 1500 字**，超過時先檢查是不是塞了不只一個重點，收斂重點，不要靠壓縮句子硬塞。
2. **不用系列連載慣用的「開場、小結」骨架式段落**，一封信讀起來該像一封信。
3. **不假設訂閱者看過前面任何一期**，要提到之前講過的東西，用一句話帶過就好。
4. **語氣口語**，直接對讀者說話，像寫信給一個具體的人。
5. **每一期只服務一個具體的卡關情境**，動筆前先確認這期解決的是「寫給誰看」欄位裡那個人的哪一個問題。
6. **避免「不是…而是…」句型**，這是長文寫作已經明確要避開的 AI 腔。
