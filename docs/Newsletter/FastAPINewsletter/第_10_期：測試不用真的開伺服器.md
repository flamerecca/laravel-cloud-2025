# 測試不用真的開伺服器

跑一次測試要等 30 秒，你以為是測試太多嗎？多半是因為每個測試都在連那顆真的資料庫，建連線、寫資料、再想辦法把資料清乾淨。更糟的是，哪天有人在開發機上多塞了一筆書，原本會過的測試就紅了。

這封信只講一件事：怎麼讓 FastAPI 的測試不開伺服器、不碰真實資料庫，跑起來又快又乾淨。

## 先不管資料庫，用 TestClient 打一支路由

`TestClient` 是 FastAPI 提供的測試用客戶端，它直接在 Process 內呼叫你的 `app`，不需要 `uvicorn`，也不佔用 Port。官方文件說它依賴 `httpx`，所以要先裝：

```console
$ uv add httpx pytest
```

假設你有一支查書的路由，找不到時回 404：

```python
@app.get("/books/{book_id}")
def read_book(book_id: int, session: SessionDep):
    book = session.get(Book, book_id)
    if book is None:
        raise HTTPException(status_code=404, detail="Book not found")
    return book
```

這裡的 `SessionDep` 是一個用 `Depends` 包起來的依賴，意思是每個請求進來，由 FastAPI 呼叫 `get_session` 拿一個資料庫 Session 給路由用。

重點就在這裡：既然 Session 是 FastAPI 在請求當下才呼叫 `get_session` 拿來的，測試時我們就有機會讓它改拿別的東西。

## 把 get_session 整個換掉

`app.dependency_overrides` 是一個普通的 `dict`，key 放原本的依賴函式，value 放替代品。登記之後，FastAPI 遇到 `get_session` 就改呼叫你放進去的那個函式。

替代品要指向哪裡？一個只存在於記憶體的 SQLite。先用 pytest fixture 建好引擎與資料表：

```python
@pytest.fixture
def session():
    engine = create_engine(
        "sqlite://",
        connect_args={"check_same_thread": False},
        poolclass=StaticPool,
    )
    SQLModel.metadata.create_all(engine)
    with Session(engine) as session:
        yield session
```

`"sqlite://"` 後面沒有檔名，資料庫就只活在記憶體裡。另外兩個參數很容易被當成雜訊刪掉，但官方的 SQLModel 測試教學都有保留它們：記憶體內的 SQLite 預設每條連線各自擁有一顆空資料庫，加上 `StaticPool`，連線才會共用同一顆；`check_same_thread=False` 則讓這條連線可以被不同執行緒使用。少了它們，你可能會遇到資料表在路由裡查不到的狀況。

接著第二個 fixture 負責登記替換、交出客戶端，測試結束再清掉：

```python
@pytest.fixture
def client(session):
    app.dependency_overrides[get_session] = lambda: session
    yield TestClient(app)
    app.dependency_overrides.clear()
```

最後一行值得留著。`dependency_overrides` 掛在全域唯一的 `app` 上，不清掉，替換就可能殘留到下一個測試。官方文件把重設的做法寫得很明白，就是把它清成空的 `dict`。

這種測試時把依賴整個換成替身，不動路由本身一行程式碼的做法，就是 `dependency_overrides`，也是 FastAPI 測試的關鍵一行。

## 兩個測試，一個 200 一個 404

fixture 備好，測試本身就很短了。每個測試拿到的都是全新的空資料庫，需要什麼資料自己放：

```python
def test_read_book(client, session):
    session.add(Book(id=1, title="Python 入門"))
    session.commit()
    resp = client.get("/books/1")
    assert resp.status_code == 200
    assert resp.json()["title"] == "Python 入門"

def test_book_not_found(client):
    assert client.get("/books/999").status_code == 404
```

留意這兩個測試都是普通的 `def`，呼叫 `client.get` 也不用 `await`。官方文件特別強調這點，只有當你要在測試裡另外呼叫非同步函式時，才需要去看進階的非同步測試。

執行 `uv run pytest`，沒有伺服器要啟動，沒有資料要清，每個測試結束，記憶體裡那顆資料庫就跟著 Session 一起消失。

## 這封信帶走的東西

用 `TestClient` 直接呼叫 `app`，用 `app.dependency_overrides[get_session]` 把真實 Session 換成記憶體內 SQLite，替換與清理都寫進 fixture，每個測試就會拿到一顆乾淨的資料庫。

測試全綠了，不代表換個環境還是綠的。記憶體內 SQLite 和正式環境的資料庫連線方式、密鑰與設定都不一樣，下一封要談的是，同一份程式怎麼在本機、測試、正式三個環境都跑得起來。

回信告訴我，你現在專案的測試是怎麼跑的：全部連真實資料庫、用替身，還是還沒開始寫？如果這封信是朋友轉給你的，歡迎訂閱，每週一封。

## 待實測項目

以下項目我無法執行程式碼，目前只依官方文件確認到敘述層級，請在 Python 3.12 與系列鎖定的 FastAPI、SQLModel 版本上實測後再發信：

1. 全部程式碼區塊需實際組裝成可執行的 `main.py` 與 `test_main.py`，跑 `uv run pytest` 確認兩個測試通過。路由範例中的 `Book` 模型、`SessionDep`、`get_session` 以及測試檔的 import 都需要補齊，並確認與第 8 期的定義一致。
2. `TestClient` 依賴 `httpx`，依官方測試頁面為 `uv add httpx`。確認目前版本是否仍需手動安裝，以及規格書提的「是否需要額外套件」在鎖定版本上的實際情況。
3. 記憶體內 SQLite 的 `StaticPool` 與 `check_same_thread=False`：官方 SQLModel 測試頁面有此組態，但「少了它們資料表查不到」的症狀需拿掉兩個參數各實測一次，確認錯誤訊息與出現時機，不確定的話改寫成更保守的說法。
4. `lambda: session` 作為 `get_session` 的替代品，官方範例是用具名函式。需實測 lambda 版本可正常運作，且與原本以 `yield` 管理 Session 的 `get_session` 簽章不衝突。
5. `app.dependency_overrides.clear()` 與官方範例中的 `app.dependency_overrides = {}` 效果相同，但官方 SQLModel 頁面使用 `clear()`，需實測兩者在跨測試時都能正確還原。
6. 「不清除 `dependency_overrides` 會殘留到下一個測試」是依全域 `app` 物件推論，官方頁面只寫可以重設，未寫為必要。需設計兩個測試實測殘留造成的後果，措辭視結果調整。
7. 開場的「30 秒」是情境描述，沒有量測依據，發信前改成自己量過的數字，或改寫成不含具體數字的說法。
8. 路由範例中 `Book` 回傳為 SQLModel 物件，確認直接回傳的 JSON 欄位名稱與 `title` 吻合，必要時加上 `response_model`。
