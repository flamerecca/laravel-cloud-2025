# 你寫的型別提示，其實是一道門

前端同事丟來一張截圖，上面是一包 JSON，最上面一行寫著 422。他附了一句：「我明明有傳 id。」

你點開 Network 面板，請求網址是 `/books/abc`，id 確實有傳，只是傳的是 `abc`。問題是伺服器端你沒寫過任何檢查，它怎麼知道不對？

答案在函式簽章上。FastAPI 的路由是用裝飾器掛在函式上的，而函式參數後面那個型別提示，它會當成確認規則來執行。

## 路徑參數：型別就是規則

先看一支最小的路由：

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/books/{book_id}")
def read_book(book_id: int):
    return {"book_id": book_id}

@app.get("/books")
def list_books(limit: int = 10, keyword: str | None = None):
    return {"limit": limit, "keyword": keyword}
```

`{book_id}` 出現在路徑上，函式又有同名參數，FastAPI 就把它視為路徑參數。`book_id: int` 這個標註讓它在呼叫你的函式之前，先把字串轉成整數。轉得成，你拿到的就是真正的 `int`。轉不成，函式根本不會被執行。

請求 `/books/abc` 時，回應會長這樣，這是官方文件對非整數路徑參數展示的結構：

```json
{
  "detail": [
    {
      "type": "int_parsing",
      "loc": ["path", "book_id"],
      "msg": "Input should be a valid integer, unable to parse string as an integer",
      "input": "abc"
    }
  ]
}
```

逐欄讀的話很簡單。`detail` 是一個陣列，一個欄位出錯就多一筆。`loc` 告訴你錯在哪，第一個元素是來源，這裡是 `path`，第二個是參數名稱 `book_id`。`type` 是機器讀的錯誤代碼，`msg` 是給人讀的說明，`input` 則是它實際收到的值。把 `loc` 和 `input` 一起看，前端同事那句「我明明有傳」就有答案了：傳了，但傳的是 `abc`。

這種把函式簽章上的型別標註直接當作請求確認規則的行為，就是這封信想講的重點：型別提示在 FastAPI 裡是一道門，擋在你的函式前面。

## 查詢參數：不在路徑上，就是查詢參數

上面第二支路由裡的 `limit` 和 `keyword` 沒有出現在路徑上，FastAPI 一律把它們視為查詢參數，也就是網址 `?` 後面那一串。判斷規則只有一條：有預設值就選填，沒有預設值就必填。

所以 `limit: int = 10` 不傳會用 10，傳 `?limit=abc` 一樣吃 422，只是 `loc` 的第一個元素會變成 `query`。`keyword: str | None = None` 則是選填，沒傳就是 `None`。至於寫法，官方文件的查詢參數頁面目前範例用的是 `str | None`，沒有看到 `Optional`。

如果把 `limit` 的預設值拿掉，變成 `limit: int`，它就變成必填。漏傳時你會收到 `type` 為 `missing`、`msg` 為 `Field required` 的 422，`input` 是 `null`。

同一個名稱，出現在路徑上就是路徑參數，不在路徑上就是查詢參數，處理方式完全不同。

## 宣告順序會影響比對

還有一個很容易踩的坑。假設你想加一支 `/books/me`，回傳目前登入者借的書：

```python
@app.get("/books/me")
def read_my_books():
    return {"owner": "me"}

@app.get("/books/{book_id}")
def read_book(book_id: int):
    return {"book_id": book_id}
```

FastAPI 是依宣告順序比對路徑，所以固定路徑要寫在前面。官方文件的說法是，若順序顛倒，`/books/{book_id}` 會把 `me` 當成參數值先接走。在我們的例子裡，因為 `book_id` 標了 `int`，顛倒之後打 `/books/me` 會得到一個 422，你預期的那支路由根本沒機會執行。

## 這封信帶走的東西

函式參數上的型別提示會變成確認規則，出錯時回 422，讀 `loc` 看哪裡錯，讀 `input` 看收到什麼。在路徑上的參數是路徑參數，不在路徑上的是查詢參數，有預設值就選填。固定路徑記得寫在帶參數的路徑前面。

## 待實測項目

以下項目我無法執行程式碼，只查了官方文件（path-params 與 query-params 頁面）。請在 Python 3.12 與本系列鎖定的 FastAPI 版本實測後再發信：

1. 兩段完整程式碼需實際啟動，用 `curl` 或 `/docs` 確認可執行。
2. 422 回應 JSON 的實際結構：官方文件範例只有 `type`、`loc`、`msg`、`input` 四個欄位，但實際版本的回應可能多出 `url` 欄位，需實測後依實際輸出修改 JSON 範例與欄位說明。文件頁面未明確寫出狀態碼，需確認為 422。
3. `/books/abc` 的 `input` 為字串 `"abc"`，`msg` 文字是否與範例逐字相同，需以實測輸出為準。
4. 缺少必填查詢參數時，`type` 為 `missing`、`msg` 為 `Field required`、`input` 為 `null`，來自官方文件範例，需實測。
5. 將預設值移除後 `limit: int` 的必填行為，需實測。
6. 路由順序：官方文件只說明 `str` 型別的情境。稿中「`book_id: int` 時，順序顛倒會讓 `/books/me` 回 422」是依文件邏輯推論，並非文件原文，必須實測兩種宣告順序的實際回應。
7. `Optional` 與 `str | None` 的建議：目前只確認查詢參數頁面範例用 `str | None`，未找到文件明確標示 `Optional` 的建議地位，稿中措辭僅描述範例現況，發信前再看一次頁面。
8. 路由順序範例的第二段程式碼為片段，需與第一段合併為同一個檔案才能執行，實測時確認。
