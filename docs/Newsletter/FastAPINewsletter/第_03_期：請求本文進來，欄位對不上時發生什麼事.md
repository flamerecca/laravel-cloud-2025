# 請求本文進來，欄位對不上時發生什麼事

前端傳來一張 Network 面板的截圖，說：「欄位明明有送。」你回一張 log 截圖，說：「我這邊就是沒收到。」兩邊來回三輪，最後發現是 `pages` 被送成了 `"12"`，或是 `title` 少打了一個字母。

這封信要做的事很單純：讓你在看到請求之前，就能預測缺欄位、多欄位、型別不符這三種情況各自會發生什麼。其中一種會悄悄放行，最容易出事。

## 先有一個模型

FastAPI 的規則很短：路由函式的參數型別如果是 Pydantic 模型，它就被當成請求本文，從 JSON 讀進來。以書籍新增為例：

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class BookCreate(BaseModel):
    title: str
    pages: int

@app.post("/books")
def create_book(book: BookCreate):
    return book
```

`title` 和 `pages` 都沒有預設值，所以兩個都是必填。以下三種情況，都以這個模型為準。

## 三種對不上，三種結果

先看缺欄位。送出 `{"title": "FastAPI"}`，沒有 `pages`，FastAPI 會直接回 422，路由函式根本不會被執行。回應本文裡的 `detail` 會指出缺的是哪個欄位，前端拿這份內容就能定位，不必猜。

再看多欄位。送出 `{"title": "FastAPI", "pages": 200, "isbn": "123"}`，`isbn` 沒有在模型裡宣告。Pydantic v2 的預設是忽略多餘的資料，請求會成功，`isbn` 被丟掉，函式裡的 `book` 根本沒有這個屬性。前端以為存進去了，後端手上什麼也沒有，這就是會悄悄放行的那一種。

最後是型別不符，要分兩個小情況。送 `"pages": "12"`，Pydantic 預設採寬鬆模式，字串 `"12"` 是合法的整數寫法，所以會被轉成 `12` 放行。送 `"pages": "abc"` 就轉不了，回 422。

整理成一張表：

| 情況 | 範例 | 預設結果 |
| :--- | :--- | :--- |
| 缺必填欄位 | 少了 `pages` | 422，函式不執行 |
| 多出未宣告欄位 | 多了 `isbn` | 請求成功，多餘欄位被忽略 |
| 型別不符 | `"pages": "12"` | 轉型成 `12` 後放行 |
| 型別不符且無法轉換 | `"pages": "abc"` | 422 |

這張表的重點是第二列和第三列：預設行為偏寬容，不會替你擋下欄位名稱打錯，也不會要求型別一字不差。

## 想要更嚴格，怎麼收緊

多欄位的處理，在模型裡加一行設定就能改成拒絕：

```python
from pydantic import BaseModel, ConfigDict

class BookCreate(BaseModel):
    model_config = ConfigDict(extra="forbid")

    title: str
    pages: int
```

加上之後，`isbn` 這類未宣告的欄位會讓請求回 422，前端打錯欄位名稱的當下就會發現。

型別不符也有對應的開關。Pydantic 有嚴格模式，可以在模型的 `ConfigDict` 設定 `strict=True`，或在單一欄位的 `Field` 上設定 `strict=True`。依官方的轉換表，JSON 輸入在嚴格模式下，字串 `"12"` 不會再被接受為整數。要不要開，看你跟前端約定的鬆緊程度。

## 用 Field 補上基本限制

型別只能擋掉「是不是整數」，擋不了「頁數是 0」或「書名是空字串」。這時候用 `Field`：

```python
from pydantic import BaseModel, Field

class BookCreate(BaseModel):
    title: str = Field(min_length=1, max_length=100)
    pages: int = Field(gt=0)
```

`min_length` 與 `max_length` 限制字串長度，`gt=0` 要求數值大於 0。違反任何一條，同樣是 422。這些限制也會同步出現在自動產生的 `/docs` 裡，前端不用再來問你書名最長幾個字。

## 這封信帶走的東西

缺欄位會被擋下，多欄位預設被忽略，`"12"` 這類看起來像整數的字串預設會被轉型。想讓多欄位也被擋下，加 `extra="forbid"`；想讓型別一字不差，開嚴格模式；想限制長度與範圍，用 `Field`。

下一封要看的是反方向：請求管好了，回應出去的時候，又該怎麼控制哪些欄位能被看到。

回信告訴我，你的團隊現在怎麼約定前後端欄位，是共用文件、靠 OpenAPI，還是靠截圖對答案。如果這封信是朋友轉給你的，歡迎訂閱，每週一封。

## 待實測項目

以下項目我無法執行程式碼，只查到官方文件說法，請在 Python 3.12、Pydantic v2 與目前 FastAPI 版本實測後再發信：

1. 四段程式碼都需要實際啟動，用 `curl` 或 `/docs` 確認可執行，且每段 ≤ 15 行。
2. 缺欄位回 422：官方 body 頁面只說會回「清楚的錯誤」，未給 JSON 範例。需實測確認狀態碼，並確認 `detail` 內以 `loc` 指出缺的欄位，再決定是否在信中貼出實際回應。
3. 多餘欄位預設被忽略：Pydantic 官方 models 頁面明確寫預設為 `'ignore'`，但規格書要求實測，需確認在 FastAPI 路由中回傳的 `book` 不含 `isbn`。
4. 字串 `"12"` 傳入 `int` 欄位：官方轉換表顯示 JSON 輸入的寬鬆模式接受，需實測確認回傳 `pages` 為數字 `12`，以及 `"abc"` 回 422。
5. `extra="forbid"`：Pydantic 官方頁面沒有給出完整的 forbid 範例，只有 `extra='allow'` 的寫法並註明改成 `'forbid'` 會失敗。稿中的 `ConfigDict(extra="forbid")` 寫法需實測確認，包含回 422 與錯誤內容。
6. 嚴格模式：稿中「JSON 輸入在嚴格模式下 `"12"` 不被接受」依官方轉換表的 JSON Strict 表推得，尚未實測。需分別測模型層 `ConfigDict(strict=True)` 與欄位層 `Field(strict=True)`；另外要確認經 FastAPI 傳入時，請求本文是否確實以 JSON 模式驗證。
7. `Field` 限制違反時回 422，以及限制是否出現在 `/docs` 的 schema 中，需實測。
8. 稿中「`gt=0` 要求大於 0」的範例，需測 `pages` 為 0 與負數兩種情況。
9. 版本號：本系列鎖定的 FastAPI 與 Pydantic 版本需確認，稿中未寫任何具體版本號。
