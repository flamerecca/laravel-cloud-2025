# 例外丟出去之後，使用者看到的是什麼

客戶傳來一張截圖，畫面中央只有一行字：Internal Server Error。你打開日誌，發現只是某個查詢沒找到書，路由裡的 `None` 被直接拿去讀屬性。客戶看到的是 500，前端同事看到的是一段沒辦法解析的純文字，而你什麼細節都不想讓他們看到。

一句話交代背景：路由裡丟出的例外如果沒人攔截，用戶端最後拿到的就是 500。這封信要做的，是讓每一種錯誤都回到同一個格式。

## 先用 HTTPException 處理預期內的錯誤

找不到資源，是你預期會發生的事，直接丟 `HTTPException` 並指定狀態碼：

```python
from fastapi import FastAPI, HTTPException

app = FastAPI()
books = {1: "Fluent Python"}

@app.get("/books/{book_id}")
def read_book(book_id: int):
    if book_id not in books:
        raise HTTPException(status_code=404, detail="Book not found")
    return {"title": books[book_id]}
```

官方文件提醒過，它是 Python 例外，要 `raise`，不能 `return`。回應本文會長成 `{"detail": "Book not found"}`。

問題來了：`detail` 是 FastAPI 的預設鍵名，而你的團隊也許早就約定錯誤要長成別的樣子。專案一大，每個人自己丟 `HTTPException`，`detail` 裡有人放字串，有人放字典，前端就得寫一堆分支。

## 自訂例外類別，加上對應的處理器

比較穩的做法，是讓業務邏輯只丟有意義的例外，格式交給一個地方統一產生。先約定錯誤回應固定含 `code` 與 `message` 兩個欄位：

```python
from fastapi import Request
from fastapi.responses import JSONResponse

class BookNotFound(Exception):
    def __init__(self, book_id: int):
        self.book_id = book_id

@app.exception_handler(BookNotFound)
async def book_not_found(request: Request, exc: BookNotFound):
    return JSONResponse(
        status_code=404,
        content={"code": "BOOK_NOT_FOUND", "message": f"找不到書籍 {exc.book_id}"},
    )
```

路由裡改成 `raise BookNotFound(book_id)`，其餘都不用管。換狀態碼、換訊息，只動處理器一處。

## 兜底處理器：記錄日誌，不回傳細節

沒預期到的例外怎麼辦？註冊一個針對 `Exception` 的處理器，把細節寫進日誌，對外只回固定的通用訊息：

```python
import logging

logger = logging.getLogger("app")

@app.exception_handler(Exception)
async def fallback(request: Request, exc: Exception):
    logger.error("未處理例外 %s", request.url.path, exc_info=exc)
    return JSONResponse(
        status_code=500,
        content={"code": "INTERNAL_ERROR", "message": "伺服器發生錯誤"},
    )
```

這裡有兩個重點。第一，堆疊追蹤、SQL 語句、檔案路徑，全部只進日誌，不進回應本文。第二，Starlette 文件說明，註冊在 `Exception` 或 500 上的處理器由最外層的 `ServerErrorMiddleware` 執行，而且開啟除錯模式時，Starlette 會改回傳含堆疊追蹤的頁面，不再使用你裝的 500 處理器。所以除錯模式只該留在本機，正式環境務必關掉。

## 連 422 也改成同一個格式

請求欄位對不上時，FastAPI 預設回 422，格式是它自己的。想讓前端只處理一種結構，覆寫 `RequestValidationError` 的處理器：

```python
from fastapi.exceptions import RequestValidationError

@app.exception_handler(RequestValidationError)
async def invalid_request(request: Request, exc: RequestValidationError):
    return JSONResponse(
        status_code=422,
        content={"code": "INVALID_REQUEST", "message": "請求欄位不正確"},
    )
```

官方文件有一段警告值得記住：`RequestValidationError` 帶有檔名與行號等資訊，直接轉成字串回傳，可能洩漏系統細節。要回欄位細節的話，用 `exc.errors()` 逐筆取出需要的部分，不要整包丟出去。

前面第一段的 `HTTPException` 也一樣，預設仍然是 `{"detail": ...}`。官方建議註冊處理器時用 Starlette 的 `HTTPException`，這樣 Starlette 內部丟出的 404 與 405 也會被一併接住。

## 這封信帶走的東西

預期內的錯誤丟自訂例外，格式集中在 `exception_handler` 一處產生。`Exception` 兜底處理器只記日誌、只回通用訊息，422 也改寫成同一組 `code` 與 `message`。這樣用戶端永遠只看到你決定給它看的東西。
