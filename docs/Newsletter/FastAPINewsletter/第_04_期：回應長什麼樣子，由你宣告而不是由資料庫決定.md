# 回應長什麼樣子，由你宣告而不是由資料庫決定

上週 code review，我在一支註冊 API 的回應裡看到一個欄位：`hashed_password`。寫的人沒有惡意，他只是把剛建好的使用者物件直接 `return` 了出去，心想前端拿到 id 和名稱就夠用。結果前端確實拿到了，連同整串雜湊值一起。

這種事不會在你自己測試時發現，因為回應看起來「正常」，一切都有回來。

## 路由回傳什麼，用戶端就收到什麼

FastAPI 的規則很單純：路由函式回傳什麼，它就轉成 JSON 送出去。回傳的東西裡有幾個欄位，用戶端就看到幾個欄位。

假設註冊時，輸入是一個 Pydantic 類別 `UserCreate`，裡面有 `username` 和 `password`。路由收到之後，把密碼雜湊，整包丟回去：

```python
def fake_hash(raw: str) -> str:
    return "hashed:" + raw

@app.post("/users")
def create_user(user: UserCreate):
    return {
        "username": user.username,
        "hashed_password": fake_hash(user.password),
    }
```

這裡的 `fake_hash` 只是示意用的替身，正式環境請用真正的雜湊函式庫。重點在回應：

```json
{"username": "recca", "hashed_password": "hashed:secret"}
```

路由裡每多一個欄位，回應就多一個欄位，沒有人替你把關。

## 在路由上宣告輸出長什麼樣

修法是多寫一個類別，專門描述「可以給人看的樣子」，再用 `response_model` 告訴 FastAPI：

```python
from pydantic import BaseModel

class UserCreate(BaseModel):
    username: str
    password: str

class UserPublic(BaseModel):
    username: str

@app.post("/users", response_model=UserPublic, status_code=201)
def create_user(user: UserCreate):
    return {"username": user.username, "hashed_password": fake_hash(user.password)}
```

路由裡的回傳內容完全沒變，連 `hashed_password` 都還在。但 FastAPI 在送出之前，會拿 `UserPublic` 來過濾，沒有宣告的欄位一律不會出現在回應裡，用戶端收到的只剩：

```json
{"username": "recca"}
```

輸入用 `UserCreate`，輸出用 `UserPublic`，兩個類別各管一邊。這樣寫多了幾行，換來的是一個明確的邊界：以後資料表加了 `is_admin`、`last_login_ip` 之類的欄位，除非你主動寫進 `UserPublic`，否則不會自己溜出去。

這套做法有個名字，叫輸入輸出模型分離。回應的欄位清單是你寫在 `UserPublic` 裡的契約，不由資料庫的欄位決定。

## 官方更偏好哪種寫法

你可能在別的教學看過另一種寫法，直接在函式上標註回傳型別，例如 `-> UserPublic`。官方文件目前的重點是：只要回傳型別就是你要的輸出模型，標註回傳型別可以讓編輯器和型別檢查工具一起幫忙。但函式實際回傳的內容和要對外公開的模型不是同一個類別時，回傳型別標不出你想要的輸出，這時就要用 `response_model` 參數。官方範例也是這樣處理的，函式標 `-> Any`，過濾交給 `response_model`。

如果兩個參數同時存在，以 `response_model` 為準。

## 狀態碼也順手宣告

上面那段程式碼的裝飾器還有一個 `status_code=201`。`POST` 成功建立資源，慣例回 201 Created，FastAPI 預設是 200，不會替你改。

順帶一提，刪除成功常見回 204 No Content。依官方文件，204 的回應不能有本文，所以這種路由不要再 `return` 一個 JSON 物件出去。

## 這封信帶走的東西

寫路由的時候，別讓回傳內容決定用戶端看到什麼。輸入一個模型，輸出另一個模型，用 `response_model` 接起來，再用 `status_code` 標明建立成功是 201。

下一封要看的是另一個重複問題：每支路由都要分頁參數、都要取目前使用者，這些重複的程式碼該放在哪。

回信告訴我，你現在手上的 API 有沒有哪支路由回傳的欄位比前端需要的多。打開一支列表或註冊的路由，看一眼實際回應就知道了。如果這封信是朋友轉給你的，歡迎訂閱，每週一封。
