# 同一份程式，怎麼在三個環境跑起來

把資料庫密碼 commit 進 Git 的那一刻，通常沒人覺得有問題，因為當下只是想讓本機先跑起來。問題出在幾週後：測試環境的資料庫位址不一樣，你改了一行；正式環境又不一樣，你再改一行；然後某天有人把那行改動合進主線，密碼也跟著留在歷史紀錄裡，刪不乾淨。

這封信只處理一件事：讓同一份程式碼在本機、測試、正式環境都能跑，差別只在外面塞進去的環境變數，程式碼本身一個字都不用改。

## 把組態設定收進一個 Settings 類別

`pydantic-settings` 是獨立套件，要另外安裝。它的 `BaseSettings` 會依欄位名稱去讀環境變數，大小寫不拘，讀進來還會照型別提示轉型與確認：

```python
from functools import lru_cache
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")

    database_url: str
    secret_key: str

@lru_cache
def get_settings() -> Settings:
    return Settings()
```

`database_url` 沒有預設值，所以環境變數 `DATABASE_URL` 沒設時，程式在啟動讀設定的那一刻就會報錯，不會拖到第一個請求打到資料庫才爆。密鑰缺了，寧願服務根本起不來。

`env_file=".env"` 讓本機開發可以把值寫在檔案裡。依 pydantic-settings 官方文件，環境變數的優先順序高於 `.env` 檔，所以在正式環境直接設環境變數，就會蓋過檔案裡的值。這個檔案要加進 `.gitignore`，它存在的目的就是只活在你的機器上。`extra="ignore"` 則是讓 `.env` 裡出現 Settings 沒宣告的鍵時不會直接報錯。

`@lru_cache` 的用意是讓 `Settings()` 只建立一次，不用每個請求都重新讀一次檔案。

## 用 Depends 把設定交給路由

路由不要自己 `import` 一個全域的 settings 物件，改用 `Depends` 接進來：

```python
from typing import Annotated
from fastapi import Depends, FastAPI

app = FastAPI()

@app.get("/health")
def health(settings: Annotated[Settings, Depends(get_settings)]):
    return {"secret_configured": bool(settings.secret_key)}
```

好處是測試時可以用 `dependency_overrides` 把 `get_settings` 換成指向測試資料庫的版本，路由本身不用動。

## uvicorn 還是 gunicorn

本機開發用 `uvicorn main:app --reload`，改了程式碼自動重啟，這部分沒有爭議。

到了正式環境，要看你的服務怎麼被管理。依 FastAPI 官方部署文件目前的說法，如果你跑在 Kubernetes 這類會替你做複本管理的環境，每個容器只跑一個 Uvicorn Process，複本數交給編排工具調整。若只是一台機器、沒有編排工具，才考慮在單一容器裡開多個 Worker，官方文件示範的做法是 `--workers` 參數。

那 `gunicorn` 呢？官方 Docker 文件提到，早期需要 `gunicorn` 是因為 Uvicorn 當時無法自己管理並重啟掛掉的 Worker，現在 Uvicorn 自己支援 `--workers`，多數情境不必再多疊一層。如果你的團隊已經有 `gunicorn` 的維運習慣，搭配 Uvicorn 的 Worker 類別仍然可行，只是這時你多了一層要維護的設定。

判斷條件很直接：有編排工具，就一個容器一個 Process；單機部署，先用 `--workers`；有既有 `gunicorn` 流程，再考慮疊上去。

## 最小的 Dockerfile

重點只有兩個，相依套件先安裝，還有別用 root 跑：

```dockerfile
FROM python:3.12-slim
WORKDIR /code
RUN useradd --create-home appuser
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY ./app ./app
USER appuser
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

`requirements.txt` 比程式碼少變動，先單獨複製並安裝，Docker 就能在你只改程式碼時重用那一層快取，建置快很多。`CMD` 用陣列寫法，官方文件特別建議，這樣服務才能正常收到結束訊號並收尾。

密鑰與資料庫位址不寫進映像檔，執行時再傳進去，同一個映像檔從測試搬到正式環境都不用重建：

```bash
docker run -e DATABASE_URL="..." -e SECRET_KEY="..." -p 8000:8000 my-api
```

## 這封信帶走的東西

組態設定交給 `BaseSettings` 從環境變數讀，環境變數優先於 `.env`，`.env` 不進版本控制。正式環境的啟動方式看你有沒有編排工具來決定 Worker 數，映像檔裡相依套件先裝、不用 root 跑。

## 待實測項目

以下項目我無法執行程式碼或建置映像檔，已用官方文件確認說法，其餘須實測後再發信：

1. Settings 類別與 `/health` 路由需在目前 FastAPI 與 pydantic-settings 版本實際啟動。分別驗證：未設 `DATABASE_URL` 與 `SECRET_KEY` 時啟動報錯、只有 `.env` 時可讀到、同時設環境變數與 `.env` 時環境變數勝出。
2. `extra="ignore"` 的行為：在 `.env` 加一個 Settings 未宣告的鍵，確認不報錯；移除該參數後確認會報錯。官方文件說預設為 `forbid`，此處需實測。
3. Dockerfile 基底映像檔標籤。官方 FastAPI Docker 文件目前範例為 `python:3.14`，系列企劃鎖定 Python 3.12 以上，本稿寫 `python:3.12-slim`，標籤是否存在、`useradd` 在該映像檔是否可用，須實際建置。
4. Dockerfile 以 `appuser` 執行後，`pip install` 安裝的套件與 `/code/app` 是否可被該使用者讀取，並確認容器內 `uvicorn` 可找到。`requirements.txt` 內容須含 `fastapi`、`uvicorn`、`pydantic-settings`。
5. `docker run -e` 範例需實測，確認映像檔不含 `.env`，建議加 `.dockerignore` 排除，稿中未提，是否補一句待你決定。
6. 「官方文件說 Uvicorn 現在自己支援 `--workers` 所以多數情境不必再疊 `gunicorn`」，出自 FastAPI Docker 文件關於舊版 `tiangolo/uvicorn-gunicorn-fastapi` 映像檔已棄用的段落；`server-workers` 頁面本身未提及 `gunicorn`。「搭配 gunicorn 仍然可行」一句未在官方文件查到明確出處，是我的推論，發信前請確認或刪除。
7. 稿中「`CMD` 陣列寫法讓服務正常收到結束訊號」依 FastAPI 官方文件的 exec form 說明，建議實際 `docker stop` 確認收尾行為。
8. 官方部署文件目前 Docker 範例用 `fastapi run`，本稿用 `uvicorn` 以對應規格書主題，兩者擇一須與系列其他期保持一致。
9. 引用的官方頁面現況，發信當天需再看一次：fastapi.tiangolo.com 的 advanced/settings、deployment/docker、deployment/server-workers，以及 pydantic-settings 文件。
