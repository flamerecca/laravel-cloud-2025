# 「能不能做得更像我們的品牌」，這句話有三種答案

上週跟一個做內部系統的朋友聊天，他說老闆丟給他一句話：「後台可以做得更像我們的品牌一點嗎？」

他當下的反應是點頭說沒問題，回去就打開程式碼開始改。結果改到一半發現，光是要讓 Sidebar 長得不一樣，Filament 內建的元件根本不夠用，得重寫整個 Layout。原本以為兩三個小時能交差的事，拖了快一週，老闆還在納悶「不就是換個顏色而已嗎」。

問題不在他技術不夠好，問題在他一開始就沒問對問題。

## 一句話聽起來單一，代價卻天差地遠

「做得更像我們的品牌」，這句話從老闆或 PM 嘴裡說出來的時候，通常是一個模糊的整體印象，不是一份規格。它可能指的是換個主色調、把字體換成公司慣用的那套；也可能是整個版面配置都要照著品牌手冊重新設計，連頁首、選單、卡片邊框的圓角都要對齊。

這兩件事的工作量差了十倍不只。但因為需求方講出來的話聽起來一樣，很多工程師會直接跳過「釐清範圍」這一步，憑直覺選一個切入點就開始動手。

常見的翻車有兩種。一種是選錯層級做到一半，才發現內建機制撐不住，得回頭重寫，前面的時間等於白花。另一種是反應過度，明明對方只是想換個主色調，卻擔心「以後可能會加更多客製化」，於是一開始就選了成本最高的做法，花了不成比例的力氣去處理一個原本很小的需求。

這兩種翻車的共同根源是同一件事：沒有先建立一套分層的判斷依據，就急著動手。

## 三層框架：從最輕量到最深層

要避免上面那兩種狀況，可以先在腦中建立一套三層框架，把「品牌客製化」這件事按照改動深度分成三個層級。拿到需求的當下，先判斷這個需求落在哪一層，再決定怎麼做。

第一層是樣板微調，處理的是顏色、字體、間距這類表層視覺差異。這一層的判斷提示很直覺：如果需求描述裡出現的關鍵字是「換個顏色」「字體大一點」「間距抓緊一點」，那大概就是這一層，改動範圍小，也不需要動到框架底層的結構。

第二層是主題設定，處理的是整體視覺風格的調整，但這個調整還在框架本身提供的主題機制範圍內。判斷提示是：如果需求聽起來是「整個後台的質感要跟我們官網一致」「要有我們品牌的識別感」，但沒有明確要求某個頁面的版面配置要重新排列，那通常落在這一層。這一層動的是系統性的樣式設定，不是逐頁面手工調整。

第三層是完全自訂佈局，處理的是版面配置、頁面結構本身都要重新設計的需求。判斷提示是：如果對方講出「Sidebar 的排列方式要不一樣」「這個頁面的資訊架構要照我們自己的方式呈現」這類話，代表需求已經超出主題機制能調整的範圍，得動到 Layout 本身。這一層改動的是結構本身，工程量自然比前兩層高上一截。

這三層之間沒有優劣，只有對應不對應。選對層級，代價就是需求本身該有的代價；選錯層級，代價會被無謂地放大。

## 先問範圍，再選層級

三層框架本身不難記，難的是把它變成一個反射動作：拿到需求的第一件事，是問「這個改動範圍有多大」，而不是打開編輯器開始找元件。

這句自問句要問的具體一點。可以直接追問對方：「你說的更像品牌，是指顏色跟字體，還是整個版面的排列方式都要改？」多數時候，對方自己也說不清楚，但這個追問過程會逼著雙方把模糊的整體印象拆解成具體的改動範圍，而這個範圍就直接對應到三層框架裡的某一層。

這裡要老實講一件事：這期電子報不是要教你三層各自的技術做法，內建元件怎麼設定、主題檔案怎麼寫、Layout 怎麼重構，那些是選定層級之後才要處理的事，也是後面幾期會陸續拆解的內容。這期唯一想留給你的，是先問清楚範圍再動手這個習慣。

養成這個習慣之後，最大的變化不是省了多少程式碼，是省了那種「改到一半發現選錯層級」的挫折感，還有那種「花了三天做了一件其實半天就能解決的事」的懊悔。判斷邏輯這種東西平常感覺不出價值，但每次少走一次冤枉路，累積起來就是整個專案時程的差別。

下次再聽到「能不能做得更像我們的品牌」，先別急著點頭說沒問題，先在心裡把這句話拆成三層框架裡的某一層，再決定下一步。
