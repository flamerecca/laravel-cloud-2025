# 不用按重新整理，資料自己跳出來

上一期我們把一個能拖拉操作的功能真正做出來了，讀者點一下、拖一下，畫面就照著使用者的手勢更新狀態。這期要處理的是另一種互動，不是一個人操作自己的畫面，而是好幾個人同時盯著同一份資料。

想像這個場景：你們團隊在用同一個 Filament 後台管理一批訂單，客服 A 打開列表頁盯著待處理的單子，倉管 B 同時也開著同一頁在準備出貨。B 把某張訂單標成「已出貨」，存檔成功，畫面也照他的預期更新了。但 A 那邊呢，A 的畫面上，那張訂單還是「待處理」，一動也不動，直到 A 自己手動按下重新整理，才會看到 B 剛剛做的變更。

如果只是單人操作，這種延遲根本不會有人在意，反正你自己改的，你自己看得到。問題出在多人協作，而且是即時性要求高的協作，A 可能因為畫面上還顯示「待處理」，又重複處理了一次已經處理過的訂單，或者客服跟倉管在電話裡對不上資訊，各自看著各自版本的真相。這種侷限，是前面八期的客製化技巧都沒碰過的問題類型。之前不管是自訂欄位、自訂頁面，還是跳出 Schema 寫獨立元件，處理的都是「一個使用者跟自己畫面的互動」，這一期第一次要處理「一個使用者的動作，怎麼讓另一個使用者的畫面也跟著動」。

在往下講之前，先把話說清楚，因為我完全不假設你對這個機制熟悉。即時廣播機制在做的事情，簡單講就是一句話：伺服器那邊的資料一有變化，就主動把訊息推送到所有正在連線的使用者畫面上，不用等使用者自己重新整理來問一次「現在資料長怎樣」。平常我們寫的網頁互動，多半是使用者主動發出請求，伺服器才回應；即時廣播反過來，是伺服器主動敲每一個人的畫面，告訴他們「東西變了」。

這一步，我要老實跟你說清楚：接下來用的主要不是 Filament 的能力，是 Laravel 原生的即時廣播機制。這件事不歸 Filament 管，是 Laravel 這個框架本身提供的底層基礎設施，Filament 完全沒有另外發明一套推播系統。Filament 在這裡扮演的角色，是橋接，不是主角。它負責的是把即時廣播送進來的訊息，接住，轉化成畫面上某個元件狀態的更新，讓 A 的畫面在收到「B 剛剛把某張訂單標成已出貨」這個訊息之後，知道要把哪個欄位改成什麼值。訊息本身怎麼被送出去、怎麼被送進來，這一段完全是 Laravel 原生機制的工作範圍。

如果你一路跟著這系列走過來，應該能感覺到，這一步的距離比前面任何一期都遠。前八期不管跳得多深，終究還在跟 Filament 的元件、Schema、Livewire 元件生命週期打交道，是同一個框架體系裡面的事。這一期不一樣，你動用的是 Laravel 的佇列、事件系統，還有一套獨立於 Filament 之外運作的即時通訊協定。這是這條分層判斷路上，第一次真正站到框架主場之外，去借用底層工具解決問題。

那具體要串起哪些環節，這期打算用概念層級帶你過一遍，不寫完整的程式碼，因為每個專案的資料結構、廣播頻道規劃都不一樣，硬塞一段程式碼進來，你複製貼上大概率也用不了，反而模糊了重點。整條路徑其實只有三段，你不需要每一段都精通，但要知道每一段在做什麼事。

第一段是後端，資料變化的當下，觸發一個廣播事件。B 把訂單狀態改成「已出貨」存檔成功之後，這個動作要被包裝成一個事件，丟出去。第二段是廣播頻道，這個事件要被送到哪裡，誰有資格收到，這一段決定了訊息的路由，你可以把它想成一個廣播電台，事件是節目內容，頻道是頻率，只有調到那個頻率的人才收得到。第三段是前端訂閱，A 的瀏覽器要先訂閱那個頻道，才有機會收到剛剛丟出去的事件，收到之後，Filament 的元件負責把這個訊息轉譯成畫面上該更新的狀態，A 的畫面上那張訂單，才會在他什麼都沒做的情況下，自己從「待處理」變成「已出貨」。

這三段串起來，就是「資料自己跳出來」背後在發生的事。你不用一次全部搞懂，但下次卡在「多人協作，畫面對不上」這種需求的時候，至少知道該往哪個方向拆解問題，不會誤以為 Filament 藏了一個你沒找到的即時更新開關。

如果你手上剛好也有類似的需求，好幾個人要同時看到同一份資料變化，回信跟我說說你的場景，我很想知道這種多人即時同步的問題，在不同團隊裡長什麼樣子。下一期要處理的是另一個方向的問題：前面九期陸續做出不少客製化功能，程式碼開始散落在專案各個角落，該怎麼把它們收斂成可以重複拿來用的東西，而不是每個新專案都重寫一次。
