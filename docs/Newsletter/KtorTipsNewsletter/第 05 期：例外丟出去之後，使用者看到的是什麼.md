# 例外丟出去之後，使用者看到的是什麼

客戶傳來一張截圖，是一整頁堆疊追蹤，裡面有你的類別名稱、檔案路徑，還有一段 SQL。他問：「這是不是出事了？」

處理函式裡丟出去、沒有人接的例外，預設會變成 500。至於回應本文裡帶了什麼，請你現在就開著服務，故意丟一個例外，用 `curl` 看一次。這是決定你需要做多少事的第一步。

## 用 StatusPages 接住它

StatusPages 是一個 Plugin，讓你針對不同的例外型別，決定要回什麼狀態碼與內容。一個最小的組合是三層：自訂的找不到資源例外對應 404，請求格式錯誤對應 400，其他一律 500。

```kotlin
class OrderNotFound(val id: Long) : RuntimeException()

install(StatusPages) {
    exception<OrderNotFound> { call, cause ->
        call.respond(HttpStatusCode.NotFound, ErrorBody("ORDER_NOT_FOUND", "找不到訂單 ${cause.id}"))
    }
    exception<BadRequestException> { call, _ ->
        call.respond(HttpStatusCode.BadRequest, ErrorBody("BAD_REQUEST", "請求格式不正確"))
    }
    exception<Throwable> { call, cause ->
        call.application.log.error("未處理的例外", cause)
        call.respond(HttpStatusCode.InternalServerError, ErrorBody("INTERNAL_ERROR", "伺服器發生錯誤"))
    }
}
```

最後一個 `Throwable` 是兜底。注意它做的兩件事：把完整的例外記到日誌裡，方便你查；回給用戶端的只有一段固定的文字。堆疊追蹤與內部訊息只該留在日誌，不該出現在回應裡。

## 統一錯誤格式

上面範例裡的 `ErrorBody` 長這樣：

```kotlin
@Serializable
data class ErrorBody(val code: String, val message: String)
```

為什麼要統一？前端收到的錯誤如果有時是純文字、有時是 JSON、欄位名稱又不一致，每支 API 都得各自處理。約定一個固定的形狀，前端只要寫一個錯誤處理函式。`code` 給程式判斷，`message` 給人看。

## 兜底處理器要小心一件事

`Throwable` 的範圍很大，協程的取消例外也在裡面。兜底處理器會不會接到取消例外，進來之後該不該處理，請在你的版本上實測確認，不要假設框架已經幫你排除。這個問題之後談協程時還會再碰到。
