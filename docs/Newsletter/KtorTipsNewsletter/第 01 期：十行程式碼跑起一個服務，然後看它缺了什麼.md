# 十行程式碼跑起一個服務，然後看它缺了什麼

專案產生器跑完，資料夾裡躺著一堆檔案，一半你不知道是做什麼的。服務是跑起來了，但沒有任何一個檔案你敢刪，也沒有任何一行你敢改。

這封信把最小的 Ktor 專案拆開來看一次，讓你知道哪些東西是必要的，哪些可以先放著。

## 最小的服務

```kotlin
fun main() {
    embeddedServer(Netty, port = 8080) {
        routing {
            get("/health") {
                call.respondText("ok")
            }
        }
    }.start(wait = true)
}
```

逐行來看。`embeddedServer(Netty, port = 8080)` 指定用 Netty 當引擎，監聽 8080 這個 Port，Netty 是 Ktor 支援的幾種引擎之一。後面的大括號是這個應用程式的設定區塊。`routing` 在裡面登記路徑與對應的處理邏輯。`get("/health")` 是一條路由，`call` 代表當下這個請求與它的回應，`respondText` 把一段文字送回去。最後 `start(wait = true)` 啟動伺服器，並讓主執行緒停在這裡不要退出。

專案產生器預設用的是另一種啟動方式 `EngineMain`，它啟動時去讀組態檔，由組態檔決定載入哪些模組。兩種寫法做的事一樣，差別只在設定放在程式碼裡還是放在檔案裡，後面談部署時再回來看這一塊。

## 哪些檔案是必要的

最少只需要兩樣：一份 `build.gradle.kts`，宣告 Ktor 的相依與 Gradle 外掛，加上一個含 `main` 的 Kotlin 檔。

其他的東西，組態檔、日誌設定 `logback.xml`、產生器附送的範例路由、測試資料夾，有了很方便，沒有服務一樣跑得動。第一天不需要全部搞懂，可以先把它們當成後面幾期才會用到的備料。

## 它預設沒有的東西

如果你用慣 Laravel 或 Spring Boot，這個服務缺了幾樣你預設就會有的東西：依賴注入容器、資料庫存取層、認證機制、輸入驗證。

Ktor 的核心只處理一件事，把進來的 HTTP 請求交給對應的處理函式，再把回應寫回去。其他能力都是 Plugin 或另外的函式庫，裝了才有，沒裝就不存在。這是刻意的取捨：沒裝的東西不會占資源，也不會替你做決定。代價則是每一個決定都要你自己來做。

這個系列後面幾期，補的就是這些要自己決定的事：路由怎麼組織、JSON 怎麼進出、例外怎麼統一處理、資料庫怎麼接、物件怎麼組裝、認證怎麼做、測試怎麼寫，最後是部署。

服務跑起來之後，第一件事通常是多寫幾條路由，而路由寫在哪裡，會決定專案之後好不好維護。下一封信談這件事。

回信告訴我你現在最熟悉的後端框架是哪一個，後面幾期的對照會挑讀者最多的那一個。如果這封信是朋友轉給你的，歡迎訂閱，每週一封。
