# 誰說一個 Resource 只能有四個畫面

先講結論：一個 Resource 建出來，預設會有四個畫面：列表負責讓你瀏覽一整批資料，建立負責新增一筆，編輯負責改一筆，檢視負責唯讀看一筆的完整內容。大部分時候，你的需求都能塞進這四頁裡的某一頁，調欄位、調表單、調顯示方式，前三期做的事情都還在這個範圍內。

但這期要講一個不一樣的狀況：你手上的需求，四頁裡沒有一頁裝得下。

## 一個對不上任何一頁的需求

舉個例子。假設你在做一套訂單管理後台，某天業務跑來說，希望能一次選中十幾筆訂單，按一個按鈕，把它們合併成一張出貨單，同時扣掉對應的庫存、寄一封通知信給客戶。你打開 Resource 的四個畫面想找地方塞：列表頁勉強能加個按鈕，但按下去之後要做的事完全不是「看資料」，也不是「改一筆」；建立頁面對不上，因為這不是新增一筆訂單；編輯頁面更不用說，你要動的是十幾筆訂單加一份庫存，不是單筆欄位。

這種彆扭感，是這期要處理的核心。你會發現不管往哪一頁塞，都像硬把一件行李塞進不合尺寸的箱子，勉強關得上，但東西已經變形了。

這也是這個系列走到現在，第一次明顯的跳階。前三期不管是自訂表單欄位還是自訂表格呈現，本質上都是「換一個元件」，你動的是頁面裡的一小塊，列表還是列表、表單還是表單，只是裡面某一格換了長相。這一期不一樣，你要換的是整個頁面的型態，一個從頭到尾都不是在瀏覽單筆或多筆資料的操作介面。這不是同一套心法的延伸，是往下一層走。

## 骨架不會因為多一個房間而壞掉

聽到「整個頁面型態都要換」，很直覺的反應是緊張：這樣動下去，原本的架構會不會被我搞壞？列表頁還能正常運作嗎？

不會壞，這正是這期想先講清楚的事。你要做的不是拆掉原本四頁裡的任何一頁重蓋，而是在 Resource 這棟房子裡，多加蓋一個房間。原本的客廳、廚房、臥室，也就是列表、建立、編輯、檢視，照樣在原地，該怎麼用還是怎麼用，不會因為多蓋了一間而少一塊磚。新頁面是加法，不是取代，這一點值得在動手前先放進腦子裡，因為它決定了你敢不敢真的去碰這件事。

換句話說，Resource 的四頁骨架從來就不是四面牆把你關在裡面，比較像是預先幫你隔好的四個常用房間。多數需求剛好都能住進這四間裡，但如果哪天真的需要一個蒸氣室，直接加蓋一間就是了，不需要為了那一間，把整棟房子拆掉重建。

## 示範方向：掛一個完全自訂的頁面

那具體要怎麼加這個房間。概念上，你要做三件事。

第一，讓 Filament 知道這個新頁面存在，把它註冊進 Resource 底下，跟列表、建立、編輯、檢視放在同一份清單裡。第二，這個頁面需要一個自己的路由，讓瀏覽器能找得到它，同時也需要決定要不要出現在導覽選單或表格的操作按鈕裡，讓使用者摸得到入口。第三，也是最關鍵的一點，這個頁面的內容跟預設那四頁的關聯其實非常鬆散，鬆散到你可以把它想成只是借用了 Resource 這個外殼，裡面裝什麼完全由你決定。

這裡要特別點出跟前三期不一樣的地方。自訂欄位也好，自訂表格呈現也好，你終究還是活在表單或表格這套既有結構裡，只是把某一格換成自己寫的邏輯。這次的自訂頁面不受這個限制，它不必是一個表單，也不必是一張表格，可以是一個多選清單加一顆確認按鈕，可以是一段流程導引，內容形狀完全由你的需求決定，不是由 Filament 預期你會放表單或表格這件事決定。這是這期跟前面三期性質上真正的分野。

回到訂單合併的例子，這個新頁面可以是一個獨立的畫面，左邊列出可合併的訂單讓你勾選，右邊即時算出合併後的內容，按下確認才觸發真正的合併邏輯。整個過程不需要動到列表、建立、編輯、檢視裡的任何一行程式碼，它們該怎麼運作還是怎麼運作，新頁面只是安安靜靜地掛在旁邊，多了一個入口。

## 你的需求，是不是也對不上任何一頁

如果你手上正好也卡著一個怎麼塞都彆扭的功能，不管是批次操作、跨資料的彙整畫面，還是某種完全不是在瀏覽或編輯單筆資料的介面，回信告訴我這個場景長什麼樣子，我會挑幾個放進後續案例裡，讓後面的示範更貼近你實際會遇到的狀況。

下一期要處理的是另一種完全不同性質的客製化：品牌識別度。當有人跟你說「能不能做得更像我們的品牌」，這句話聽起來只有一種意思，實際上藏著至少三種代價完全不同的做法，先分清楚自己站在哪一層，再動手。
