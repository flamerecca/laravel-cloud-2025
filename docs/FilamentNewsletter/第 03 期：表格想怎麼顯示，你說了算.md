# 表格想怎麼顯示，你說了算

上一期處理的是輸入：一個表單欄位怎麼收使用者填的資料。這一期要處理的是輸出：同一筆資料，要用什麼樣子端到畫面上給人看。方向反過來了，但你會發現熟悉感遠大於陌生感。

## 表格呈現卡關的具體情境

想像一個訂單列表，裡面有個欄位存的是配送狀態，資料庫裡放的是 `pending`、`shipped`、`delivered` 這類代碼。內建的文字欄位丟出來就是原始字串，讀起來生硬，你想要的是一個有顏色的標籤，配送中是藍色，已送達是綠色，而且中文字要對得上，不是工程師看得懂的代碼。你翻了一輪內建元件的參數，能調顏色、能調字體，但就是拼不出「依資料內容決定要顯示什麼形狀跟顏色」這種邏輯。

這跟上一期卡住的地方是對稱的兩端。上一期你煩惱的是使用者要怎麼把資料塞進系統，這一期你煩惱的是系統要怎麼把資料端出來給人看。一個是資料流進來的入口，一個是資料流出去的出口，卡關的感覺很像，但發生的位置完全不同。

## 同一套邏輯，換了情境

好消息是，表格欄位跟表單欄位一樣，背後也有自己的基底類別可以繼承。擴充點的概念位置幾乎一樣，一樣是框架先把共通的事情處理好，剩下那塊你想要的獨特呈現，留給你自己補。

不一樣的地方在於，表格欄位少了表單欄位才有的那些責任，不用管資料怎麼寫回資料庫，不用管驗證規則，甚至不用管使用者互動之後狀態要怎麼變化，因為它從頭到尾就是唯讀的。少了這一大塊責任，你要覆寫的行為自然單純很多，通常就是一件事：這個值該怎麼被顯示。也因為這樣，這一期的篇幅比上一篇要短很多。

## 示範方向：唯讀版本怎麼動手

概念上，你要做的事情分三步：先挑一個表格欄位的基底類別當起點，接著決定要覆寫的是哪一段呈現邏輯，最後想清楚資料從模型欄位的原始值，到畫面上最終顯示的樣子，中間要經過什麼轉換。

這三步你聽起來是不是有點熟？挑基底類別繼承、決定要補哪一塊行為、想清楚資料怎麼轉換，上一期做自訂表單欄位的時候，你已經完整跑過一次一模一樣的流程了。

差別只在於上一期那個轉換是雙向的，使用者輸入的字串要轉成系統看得懂的格式，系統的格式又要轉回畫面上使用者填的樣子；這一期只剩單向，資料庫裡的 `shipped` 怎麼變成畫面上那個藍色的「配送中」標籤，做完就結束了，不用再考慮怎麼轉回去。

回到訂單狀態那個例子，你要做的就是在這個轉換的環節，寫一段邏輯把代碼對應到你想要的文字和顏色。這段邏輯放在哪裡、怎麼跟框架既有的渲染流程接上，用的正是你上一期已經摸過一遍的擴充點位置。

這兩期加起來，你手上其實已經握著輸入跟輸出兩端的鑰匙了。找一個你專案裡正卡著的欄位，不管是表單這邊還是表格這邊，實際去改一次看看。如果中間踩到什麼坑，回信告訴我，我很好奇大家實際卡在哪一步。下一期要處理的東西會跳大一點，不再是單一個欄位，而是整個 Resource 的頁面型態本身。
