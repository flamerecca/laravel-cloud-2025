# 內建欄位拼不出來的時候

你有沒有遇過這種表單需求：使用者要輸入一組內部編號，格式規定得很死，前三碼是英文字母加連字號，中間六碼是數字，輸入到一半還要即時判斷格式對不對，錯了要馬上變紅框提示，對了才能點下一步。你打開 Filament 的欄位清單，文字框可以，但格式驗證的即時互動它給不了；試著在文字框外面掛個 JavaScript 監聽，好像也行，但總覺得是在補丁上疊補丁，越疊越心虛。

這種時候腦子裡通常會跳出兩種念頭，一種是覺得自己一定漏看了某個內建元件，於是回頭把文件從頭滑到尾；另一種更直接，乾脆放棄用 Filament 的表單機制，自己刻一段 HTML 加 JavaScript 塞進去，能動就好。前一種想法在浪費時間，因為這個元件真的不存在；後一種想法會讓事情變複雜，因為自己刻的東西，Filament 幫你處理好的資料綁定、驗證規則、表單狀態，全部都要重寫一遍。

上一期我們建立了一個角度：這個需求離 Filament 預設的做法有多遠。今天這個編號格式的例子，離得不算太遠，還在同一個資料型態、同一種表單互動邏輯裡，只是內建元件沒有剛好長成你要的樣子。這種距離，剛好是這封信要處理的層級。

在往下講之前，先花一句話講清楚「Filament 欄位」是什麼，免得接下來的內容懸空。表單裡的每一格輸入，姓名欄、日期欄、下拉選單，背後都對應一個欄位物件，它負責定義這格輸入長什麼樣子、怎麼收使用者填的值、怎麼把值存回資料庫。你可以把它想成表單這塊拼圖裡的一片積木，每片積木各自管好自己的輸入行為。

現在回到那個編號欄位。你以為要解決它得跳出 Filament，但事實是反過來的：Filament 內建的每一個欄位，文字框、下拉選單、日期選擇器，全部都是用同一套基底類別寫出來的。框架作者當初遇到「我需要一個處理日期的輸入元件」這個需求時，做的事情跟你現在要做的事情，本質上是同一件事——挑一個基底類別，繼承它，然後定義這個欄位獨有的行為。差別只在於，那次是框架作者幫全世界的使用者定義規則，這次換成你，只為自己的這個編號格式定義規則。

繼承這件事常被誤解成「甩開框架」，但它其實是反過來的動作，是把自己接進框架已經蓋好的地基裡。表單有一整套生命週期要處理：欄位什麼時候該從資料庫把值撈出來顯示、使用者填完之後這個值怎麼被收集、送出前驗證規則怎麼跑、送出後這個值又怎麼寫回模型。這些事情繼承基底類別之後全部都是現成的，不用自己重新發明一遍。你唯一要做的，是專注在這個編號欄位獨有的那一小塊差異：長什麼樣子、輸入時怎麼即時檢查格式。

具體會經手哪些步驟，這裡用概念說一下，不落地成完整程式碼。第一步是挑基底類別，Filament 的欄位系統提供了一個所有欄位共用的父類別，裡面已經把資料怎麼進、怎麼出的機制都寫好了，你要做的是繼承它，讓自己的欄位一出生就具備這些能力。第二步是決定要覆寫哪些行為，例如這個欄位怎麼呈現在畫面上，通常會對應到一份獨立的視圖模板，你在模板裡描述輸入框長什麼樣子、格式提示放在哪裡。第三步是資料怎麼跟表單對接，欄位基底類別留了掛鉤，讓你可以在使用者輸入的原始值跟最終要存進資料庫的值之間，插入自己的轉換邏輯，比如把使用者輸入的小寫字母自動轉大寫再存檔。

```php
class ProductCodeField extends Field
{
    protected string $view = 'filament.forms.components.product-code-field';

    protected function setUp(): void
    {
        parent::setUp();

        $this->dehydrateStateUsing(
            fn ($state) => strtoupper($state ?? '')
        );
    }
}
```

這段只是示意寫法，重點不在背下這幾行怎麼寫，而在感受這件事的骨架：繼承、指定視圖、在既有的掛鉤裡插入自己的邏輯。整個過程走下來，你會發現自己一路用的都是熟悉的規則——資料從哪裡進來、驗證什麼時候跑、值最後怎麼存回去，這些都還是你做內建欄位時就在用的邏輯，只是這次沒有人幫你把「怎麼呈現」跟「怎麼即時檢查格式」這兩塊寫好，得自己補上。這正是這封信想拆掉的誤解：自訂欄位不是跳出框架另起爐灶，是在框架早就留好的擴充點上，動手補一塊內建沒附的拼圖。

如果你手上也卡著一個內建元件怎麼拼都拼不出來的表單需求，直接回信告訴我，可能會被寫進後面幾期的案例。下一期要處理的是同一套邏輯的另一半：欄位在表單裡負責收資料，那在表格清單頁面上，這些資料又該怎麼自訂顯示方式，是接下來要說的事。
