# 你加的每一個客製化，都在跟效能借錢

如果你這幾週跟著系列一路做下來，Panel 現在應該已經不太一樣了。原本很陽春的列表加了自訂欄位，表單裡塞了幾個跳出 Schema 機制的獨立元件，某個頁面甚至還做了即時互動的小工具。功能上確實豐富了不少。

但你可能也發現，某個頁面點開的時候，會有那麼一瞬間的遲滯。不是壞掉，也不是報錯，就是感覺變慢了。你打開瀏覽器開發者工具想看看是哪裡拖慢的，滑了幾下網路請求跟渲染時間軸，發現一時說不出個所以然，於是關掉分頁，想著「應該還好吧」，繼續做下一個功能。

這種說不出哪裡有問題的感覺，才是真正的問題。不是因為系統一定出了什麼大狀況，而是因為你不知道代價在哪裡，就沒辦法判斷這個代價到底值不值得付。你可能正在用一個很貴的方式，換一個其實沒那麼重要的功能。

## 這期不教技巧，只做一件事：誠實盤點

前面十期，我們陸續示範了怎麼客製化欄位、怎麼寫獨立元件、怎麼把互動邏輯塞進 Panel 裡。每一期看起來都像在告訴你「這招很好用，學起來」。但如果整個系列只有這個調性，會給人一種錯覺，好像客製化是沒有成本的萬能解法，想加就加，加了就是賺到。

不是的。這期要做的事情很單純，就是誠實面對這些客製化疊加起來之後，實際付出了什麼代價。這不是一篇效能優化技巧大全，不會教你怎麼用工具抓渲染時間，也不會給你一份效能調校清單。這期唯一的目的，是幫你建立一個判斷習慣：在動手加下一個客製化之前，先想清楚這筆帳划不划算。

## 代價具體發生在哪裡

先講清楚一件事，客製化元件變慢不是玄學，它有具體的來源。

Filament 內建的元件之所以順手，是因為框架已經幫你把狀態管理跟渲染的優化都處理好了。你用內建的 `TextInput` 或 `Select`，背後的重新渲染時機、資料同步邏輯，框架早就幫你調校過一輪。但當你寫了一個跳出 Schema 機制的獨立元件，狀態怎麼管理、什麼時候該重新渲染、資料怎麼跟外部同步，這些責任全部回到你自己身上。少了框架內建的優化，也意味著少了框架幫你兜底的效能表現，自己寫的元件，效能就得自己負責。

單一個客製化元件，代價可能還不明顯。真正容易被忽略的是疊加效應。當同一個頁面上有好幾個客製化元件同時存在，它們各自的渲染時機、各自的狀態更新，彼此之間並不是井水不犯河水。一個元件的狀態變化，可能觸發另一個元件跟著重新渲染，即使後者根本沒有必要更新。這種互相牽動的關係會隨著元件數量疊加而放大，不是一加一等於二，而是整體負擔用一種不容易預測的方式在累積。

這就是為什麼「感覺變慢」很難用單一個原因解釋。往往不是某一個元件特別糟糕，而是好幾個各自合理的客製化，湊在一起之後互相拖累。

## 把代價跟價值放上同一座天平

理解代價發生在哪裡之後，接下來要處理的問題是：那到底該不該做？

答案不是「能不做就不做」，也不是「反正能用就先加」，而是把效能代價跟這個功能帶來的實際價值，放上同一座天平一起秤。同樣的效能代價，放在不同的地方，結果可能完全不一樣。

舉個例子。假設你做了一個即時計算的客製化元件，使用者輸入數字，畫面立刻算出結果，體驗很好，但每次輸入都觸發一輪重新渲染，是有代價的。如果這個元件放在一個每天有上百人使用、業務流程的核心表單裡，這筆代價換來的是大量使用者持續受益，通常值得。但如果同樣的元件，放在一個一季可能只有兩三個人會點進去的邊緣頁面，那筆效能代價的受益人數少得可憐，多半就不值得。

功能一樣，程式碼可能幾乎一樣，值不值得做的答案卻完全相反。差別不在技術實作，而在這個功能被使用的頻率跟重要程度。這也是為什麼「該不該客製化」沒有標準答案，得回到你自己的 Panel、自己的使用情境去判斷。

下次想動手加一個客製化元件之前，不妨先問自己兩個問題：這個功能有多少人會用、多常用，以及如果不做這個客製化，退回內建元件會損失什麼。把這兩個問題的答案放在天平兩端，答案通常會比你想像中清楚。
